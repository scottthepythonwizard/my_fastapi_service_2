Final structure
sole.sneakers: one complete record per sneaker, 25 columns including generated
integer ID, category, original timestamp, reference, images and provenance.
public.favorites: (user_id,sneaker_id) primary key, ownership default auth.uid(),
created_at timestamp. User and sneaker foreign keys both use ON DELETE CASCADE.
Deleting a sneaker removes only favorites referencing it. Deleting an account
removes its favorites and administrator membership. Remaining sneakers survive.
public.sole_admins: the existing administrator membership table, unchanged.

Access
Signed-in users can read the complete catalog. Catalog INSERT/UPDATE/DELETE
requires membership in sole_admins under RLS. The existing dedicated backend
role and secret-protected FastAPI administrative routes remain trusted backend
access. Never put the backend database URL or admin bearer token in browser code.
Favorites SELECT/INSERT/DELETE are restricted to auth.uid(); no UPDATE grant.
Users cannot write sole_admins, including granting themselves membership.
Admin membership does not grant access to another user's favorites.
All three application tables have RLS enabled.

Migration 20261122094751 enabled the sole Data API schema alongside the existing
public and graphql_public schemas. Authenticator's pgrst.db_schemas now explicitly
sets that list. This SQL override takes precedence over Dashboard schema lists;
future schema exposure changes must update it, or reset it after configuring
the Dashboard. The recovery archive is not exposed. Anonymous direct access
remains denied; public website catalog access continues through FastAPI.

Client usage
Use sole-client.example.js with your existing Supabase Auth sign-in session.
addFavorite(1) ignores duplicates without changing the original timestamp.
listFavorites() returns complete sneaker details, isFavorite(1) checks status,
and removeFavorite(1) succeeds predictably even if the favorite was absent.
createSneaker(fullRecord), updateSneaker(id,fields), deleteSneaker(id) use RLS.
Supply every required detail for new sneakers; omit generated id/created_at.
Check each returned error in the calling UI. The example module is delivered;
favorite buttons/sign-in screens were not added to the existing static sites.

Appointing the first administrator
One existing administrator was preserved. To appoint another, the trusted
project owner must verify the account's UUID in Authentication > Users, then
run the following in the owner-only Supabase SQL Editor (replace the UUID):

INSERT INTO public.sole_admins(user_id)
SELECT id FROM auth.users WHERE id='VERIFIED-USER-UUID'::uuid
ON CONFLICT(user_id) DO NOTHING;

Never expose this SQL as a browser RPC or allow clients to edit membership.

Backups and recovery
Before modifying data, a private export of rows, column definitions, constraints,
policies, grants, functions and triggers was saved under the ignored local path
.local/consolidation-backup/snapshot.json. It contains account identifiers and
must remain private. A second, database-local archive was created transactionally
in sole_recovery_20261122 before changing sneaker rows. Access to that schema
was revoked from public, anon, authenticated and the runtime role. Archive tables
are snapshots, without application constraints or indexes. Do not serve them.

For rollback: stop writes and save a fresh private export first. Review and run
supabase/recovery/restore_category_tables.sql as project owner. It refuses to
discard changes when catalog rows differ from the migration snapshot. Reconcile
later changes manually rather than bypassing that guard. The tested procedure
recreates the original category tables, constraints, triggers, policies, grants
and admin RPCs. Favorites continue referencing the same parent IDs.
The API mapper fix remains compatible with flat data only: deploy the matching
previous split-schema application adapter if restoring the split architecture.
To reverse the Data API override separately:
ALTER ROLE authenticator RESET pgrst.db_schemas;
NOTIFY pgrst,'reload config';
Keep the private archive until recovery is no longer needed; do not delete it
as part of ordinary cleanup. Credentials/auth user profiles are not included in
the application snapshot; this is not a full Supabase disaster-recovery backup.
